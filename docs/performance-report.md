## 一、测试目标与方法

### 1.1 目标

量化系统在各关键路径上的性能表现，重点验证：

1. **入库吞吐**：解析 → 分块 → 向量化的端到端耗时；
2. **检索延迟**：向量检索的响应时间；
3. **流式首字时延（TTFT）**：用户感知"开始有反应"的时间；
4. **异步非阻塞**：并发请求是否相互拖累（验证 `asyncio.to_thread` 改造效果）。

### 1.2 方法

- 通过 `httpx.ASGITransport` 直接驱动真实 ASGI 应用，**绕过网络栈**，聚焦应用内部耗时。
- 使用**真实 bge-small-zh-v1.5 权重**与**真实 Chroma 持久化实例**（临时目录隔离）。
- 延迟类指标**重复取样取中位数**，降低抖动影响。
- LLM 节点先以**桩模型**测得应用侧基线（2.2–2.5 节），再在**有效 API Key** 下用真实 DeepSeek 测得端到端真值（2.6 节）。

### 1.3 测试配置

| 参数 | 值 |
|---|---|
| Embedding 模型 | bge-small-zh-v1.5（本地，512 维） |
| top_k | 4 |
| chunk_size / overlap | 500 / 50 字 |
| 向量库 | Chroma（余弦相似度） |
| 并发样本 | 3 路 |
| 检索采样 | 10 次 |
| 流式采样 | 3 次 |

## 二、性能实测结果

### 2.1 入库路径

| 指标 | 实测值 | 说明 |
|---|---|---|
| 首次入库总耗时 | **1036.9 ms** | 含首次模型预热 + 解析 + 分块 + 嵌入 + 写库 |
| 分块结果 | 2 chunks | 样本文档约 900 字 |
| 重复上传（去重命中） | 走 `find_by_hash` 短路 | 不再解析/嵌入，显著更快 |

> 首次入库耗时包含**一次性模型预热成本**，属冷启动开销；持续入库时嵌入已就绪，单文档入库将明显低于该值。

### 2.2 检索路径（真实向量检索）

| 指标 | 实测值 |
|---|---|
| 检索延迟（中位） | **10.7 ms** |
| 检索延迟（最小 / 最大） | 10.5 / 12.4 ms |

**分析**：50 个分块规模下，检索延迟稳定在 **10–12 ms** 区间，抖动极小（极差 1.9 ms），达到"毫秒级语义检索"预期。

### 2.3 嵌入吞吐

| 指标 | 实测值 | 换算 |
|---|---|---|
| 批量嵌入 20 段 | **50.3 ms** | ≈ **2.5 ms/段**，≈ **397 段/秒** |

**分析**：bge-small 为轻量模型，CPU 单机即满足演示级吞吐；入库瓶颈主要在解析与首次预热，而非嵌入。

### 2.4 流式响应（SSE）

| 指标 | 实测值 |
|---|---|
| 首字时延 TTFT（中位） | **14.0 ms** |
| 总时延（中位） | 14.1 ms |
| TTFT 样本 | 14.0 / 12.5 / 14.3 ms |

**说明**：该项**不包含真实 LLM 推理与网络往返**（桩模型即时返回）。它反映的是"请求进入 → 检索 → 组装 prompt → 首个 token 推送"的应用侧开销，即**真实 TTFT = 本值 + 上游模型首 token 时延**。检索 10.7 ms 与应用侧 3–4 ms 共同构成本值，说明应用链路本身不构成瓶颈。

### 2.5 并发表现

| 指标 | 实测值 |
|---|---|
| 3 路并发问答总耗时 | **29.8 ms** |

**分析**：3 路并发总耗时（29.8 ms）与单路量级接近（单路含检索约 14 ms + 组装），未出现串行叠加（若阻塞事件循环，3 路应为约 3 倍）。**验证 `asyncio.to_thread` 卸载阻塞调用生效**，事件循环在 IO/CPU 密集段保持可调度。

### 2.6 真实 LLM 全链路（有效 API Key）

在同配置下接入真实 DeepSeek，测得端到端真值：

| 指标 | 实测值 |
|---|---|
| 真实首字时延 TTFT（中位） | **510 ms** |
| TTFT 样本 | 969 / 493 / 510 ms（首次含连接建立） |
| 真实问答延迟（中位，9 题） | **1038 ms** |
| 单轮问答延迟区间 | 491 – 1600 ms |

**分析**：真实 TTFT ≈ 510 ms，其中应用侧（检索 10.7 ms + 组装）仅占约 3%，**其余 97% 为上游模型推理与网络耗时**——印证"应用侧不是瓶颈、流式优先"的判断。首样本 969 ms 明显高于后两次（493/510 ms），体现**连接复用**对首字时延的收益。

## 三、性能瓶颈分析

| 环节 | 耗时量级 | 是否瓶颈 | 说明 |
|---|---|---|---|
| 文档解析（PDF/DOCX） | 中 | 潜在 | 大文件解析最耗时，已 offload 到线程池 |
| 嵌入（Embedding） | 2.5 ms/段 | 否 | 轻量模型，CPU 可承受 |
| 向量检索 | 10.7 ms | 否 | 小规模稳定；数据量增长后为关注点 |
| LLM 推理 | TTFT 510 ms | **外部主瓶颈** | 占端到端首字时延约 97%，真实体验由上游主导 |
| 应用层编排 | 3–4 ms | 否 | 链路开销很低 |

**结论**：应用侧不是瓶颈；真实端到端体验的主导因素是 **LLM 上游时延**，因此**流式输出（SSE）是提升"感知速度"的正确设计**——它不缩短总时长，但把首字可见时间从"总时长"降到"TTFT"。

## 四、优化措施与效果

| 优化项 | 措施 | 效果 |
|---|---|---|
| 事件循环阻塞 | 解析/分块/嵌入/检索/写库全部 `asyncio.to_thread` | 3 路并发不叠加，验证非阻塞 |
| 空库无效调用 | 检索为空时短路，不调 LLM | 省一次上游调用，直接返回 |
| 重复上传 | SHA-256 去重 + `find_by_hash` 短路 | 跳过解析与嵌入，二次上传近乎即时 |
| 会话内存 | `OrderedDict` + LRU（上限 200） | 防长期运行内存无限增长 |
| 历史裁剪 | 按 `max_history_turns` 裁剪 | 控制 prompt 长度与上游成本 |

## 五、局限声明（如实）

1. **真实 LLM 时延已补测**：有效 Key 下测得真实 TTFT 中位 510 ms、问答中位 1038 ms（见 2.6 节）；受上游网络波动影响，多次测量存在抖动。
2. **测试规模有限**：向量库仅几十个分块，检索延迟在小规模下平稳；**万级分块下的检索延迟未测**，需在更大数据集上复测。
3. **未做持续负载/长稳测试**：本次为功能性性能采样，非压力测试（未测 QPS 上限、长时间内存曲线）。
4. **解析耗时未单独拆分**：首次入库 1036.9 ms 为聚合值，未细分解析/嵌入/写库占比。

---

## 六、结论

- 应用侧性能**满足演示与实习展示级标准**：检索毫秒级、嵌入轻量、并发非阻塞。
- 架构决策（`asyncio.to_thread`、SSE 流式、去重短路、LRU 会话）在实测中得到验证。
- **真实端到端体验的关键变量是 LLM 上游**，当前设计（流式 + 首字优先）方向正确。
- 后续如需支撑更大规模，重点应放在：向量库选型（Milvus）、检索重排（Rerank）、以及压测（QPS/长稳）。
