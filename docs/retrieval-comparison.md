## 1. 指标定义

| 指标 | 定义 | 说明 |
| --- | --- | --- |
| `Recall@k` | 金标文档出现在前 k 位记 1，否则记 0，对全部可回答样本取宏观平均 | 用户口径中的「召回率」 |
| `Precision@k` | 前 k 位中命中金标文档的条数 ÷ k，再对样本取平均 | 用户口径中的「准确率」；单金标时恒为 `Recall@k / k`；多金标（本文 v2 有 2 题）时可能高于该值 |
| `MRR@10` | 首个命中位置的倒数排名（只在前 10 位内查找），未命中记 0 | 用户口径中的「top-k 匹配精度」 |
| `MRR(全量)` | 同上但不设 k 上限 | 与 `baseline/*_baseline.json` 的 `avg_mrr` **完全同口径**，用于回归校验 |
| `延迟 中位 / P95` | 单次查询端到端耗时（含查询向量化；**不含**索引构建与模型加载）。预热 1 轮后连测 2 轮，对全部测量取中位数与 P95 | 用户口径中的「响应耗时」 |
| `索引内存` | 该方案检索索引的驻留内存。BM25 取索引构建期间 `tracemalloc` 追踪的 Python 堆峰值（含 jieba 分词中间对象，属一次性构建开销）；向量取文档向量矩阵 + 模长的 `nbytes` | 用户口径中的「内存占用」 |
| `模型内存` | 该方案运行时必需模型权重的字节数（Σ 参数量 × 元素大小），不含激活与框架开销 | 用户口径中的「内存占用」 |

评测单位：**文档级**（gold 为一份或多份完整 markdown 文档），语料为 `eval/corpus`（v1，12 份）与 `eval/corpus_v2`（v2，8 份）。

### 3.6 性能差距解读

**耗时**（同机、CPU 推理，中位数口径）

| 对比 | 倍数 |
| --- | --- |
| 纯向量(≈9 ms) / BM25(0.15 ms) | ≈ 60× |
| 混合(≈9.5 ms) / BM25 | ≈ 63× |
| 混合+Rerank(≈1.2–1.6 s) / BM25 | ≈ **0.8–1.1 万×** |
| 混合+Rerank / 混合 | ≈ 130–170× |

混合相对纯向量只增加约 0.3–0.7 ms（BM25 打分本身极快），**全部延迟成本来自 Rerank**：它要把 Top-10 候选逐条送进 `bge-reranker-base`（约 2.78 亿参数的交叉编码器）做一次前向。

**内存**

- BM25 索引约 **45.7 MB**（46.8 MB 为 tracemalloc 峰值，含 jieba 分词中间对象的一次性开销，属构建期而非稳态）。
- 向量索引 **12–24 KB**（12 份文档 × 384/512 维 float32）。
- 模型权重：BM25 **0**；纯向量/混合 **86.6 MB（英文）/ 91.4 MB（中文）**；引入 Rerank 后 **1147.3–1152.0 MB**，即净增约 **1.06 GB**。

**质量**

- v1 上 BM25 已饱和（1.0000），Rerank 的增益为 **0**；v2 上两者同为 0.9630，Rerank 增益仍为 **0**。
- Rerank 唯一被证明的收益是把混合检索的损失补回：英文模型 **0.7000 → 1.0000**、中文模型 **0.9750 → 1.0000**。而把向量通道修好（换中文模型）后，混合本身已达 0.9750，Rerank 的边际价值随之趋近于 0。
- **最关键的对照**：v2 只有 8 份文档，而粗召回候选数为 10 ≥ 8 —— 意味着 Rerank 实际上拿到了**全库**文档做精排（对它最有利的设置），即便如此它仍未超过 BM25（0.9630 = 0.9630）。

### 4.1 现有测试集（v1）画像：确实过于简单、类型集中

来源：`eval/dataset_profile.py` → `eval/baseline/dataset_profile_v1.json`

| 画像项 | 实测值 |
| --- | --- |
| 语料文档数 | 12 |
| 问题总数 | 50（可答 40 / 不可答 6 / 模糊 4） |
| 难度 / 语义 / 查询类型标注 | **无**（50/50 未标注） |
| `must_contain` 平均词数 | **1.0**（几乎全是单个数字或短标识，如 `["512维"]`、`["rrf_k"]`、`["429"]`、`["凌晨2:00"]`） |
| 问题与金标文档的词面重合度 | 中位 **0.667**（min 0.167 / p25 0.600 / p75 0.800 / max 0.857） |
| 近逐字复述（重合度 ≥ 0.8） | **11 / 40 = 27.5%** |

三条具体证据说明问题过于简单：

1. **近乎逐字复述**。例：问题「公司每周的标准工时是多少小时？」↔ 文档原文「每周标准工时 40 小时」；问题「分块时相邻块之间保留多少字符的重叠？」↔ 文档「相邻分块重叠 50 字符」。按单字/词切分后二者几乎同构，BM25 不需要任何语义能力即可命中。
2. **题型单一**。40 道可答题全部是「单跳 + 单点事实抽取」，没有对比类、多跳类、否定排除类、指代消解类、多金标类问题。
3. **无法做切片归因**。缺少难度/语义/类型标注，且 K 固定为 1，任何分歧都无法定位到具体维度。

**后果（已由实测验证）**：BM25 在 v1 上 `Recall@1` 饱和为 1.0000，使 ③混合 与 ④Rerank 的差异被压缩到只剩「混合自己掉的那部分」；同时聚合指标完全掩盖了「向量通道其实是被英文模型拖垮」这一真相 —— 只看 0.225 会得出「向量检索在中文上不可用」的错误结论。

### 4.4 预期 vs 实测（诚实对照）

新增测试集确实拉开了 **纯向量** 与其余三方案的差距（中文模型 0.8519 vs 0.9630；英文模型 0.4815 vs 0.9259/0.9630），并暴露出唯一一道**所有方案都失败**的题：

| 失败题 | 现象 | 根因 |
| --- | --- | --- |
| q107「当前版本批量查询接口单次最多可以传多少个 ID？」（金标 `nebula_api.md`） | **四方案在两种向量模型下全部失败**（8/8）。BM25 / 混合 / Rerank 均把 `nebula_api_deprecated.md` 排在首位，纯向量则排到完全无关的 `oncall.md` | 两份文档都含「批量查询单次最多接受 N 个 ID」，字面高度重合；「当前版本」这个限定词被检索层忽略，向量也不理解「版本」这一元信息。这是**唯一一道连 Rerank 都无法纠正**的题，恰好落在 Rerank 最应该发挥作用的场景上 |

但必须如实记录一处**预期不成立**：我在 7 道「同义改写」题上预期「向量/混合优于 BM25」，实测 **BM25 的 `Recall@1` 为 1.000（全部命中）**。原因是结构性的：

> 在**文档级**检索、语料仅 8–12 份短文档时，只要问题与金标文档共享**一个**主题词，BM25 就能把该文档排到第一。同义改写只能降低字面重合度（同义改写组平均 0.602），却无法消除那唯一一个主题词。因此**无法通过「设计更难的题目」在文档级区分出 BM25、混合与 Rerank 的差距**。

这就是本次评测最重要的结构性发现：**差距之所以测不出来，不是测试集设计不够巧，而是评测粒度不对**。要真正体现三种方案的实际差距，需要同时改变四件事：

1. **升级到片段级（chunk）检索**：金标落到片段而非整篇文档，候选池从 8–12 扩大到数百，才可能出现「金标落在粗召回第 2–5 位、需要精排提升」的场景 —— 这正是 Rerank 唯一能创造价值的场景。
2. **语料规模上量**：≥ 数百份文档，拉高候选池的噪声水平。
3. **向量通道统一用生产模型** `bge-small-zh-v1.5`，否则向量与混合的数字不可信（§3.6）。
4. **补「拒答」指标**：v2 的 4 条不可答 + 3 条模糊目前仅作人工观察，未进入指标；生产链路的正确行为是检索为空时不调用大模型并返回固定话术，应把它指标化。

> 补充事实：主项目的 `scripts/evaluate.py` 已经是**片段级**口径（产出 `vector_only` / `hybrid` / `rerank` / `cache` 四个变体），`eval/` 目录这一套是**文档级消融**。建议以 `scripts/evaluate.py` 作为主评测入口，`eval/` 作为补充消融，避免两套口径互相误导。

### 5.3 口径与局限声明

1. 本报告全部为**文档级**检索指标，不含答案生成质量、幻觉率与端到端问答准确率。
2. 延迟为**单机 CPU** 实测，与部署环境、并发数、批大小强相关，不可直接外推到线上；Rerank 在中位数 1.2–1.6 s 量级，是当前链路最短的那块板。
3. 索引内存中的 BM25 值取自构建期 `tracemalloc` 峰值，含 jieba 分词中间对象的一次性开销，**不是**稳态驻留内存。
4. 模型内存只统计权重张量，不含激活、KV cache 与框架开销。
5. v2 语料仅 8 份文档，`TOP_K_RETRIEVE=10 ≥ 8`，Rerank 实际获得全库候选，属对其最有利的设置；结论在更大语料上可能变化。
6. 上述局限均不改变 §3.6 的核心结论：在当前文档级设置下，Rerank 相对 BM25 无召回增益，而延迟与内存代价极高。
